# Integrity Audit: Targeted IEEE 34-Bus FDIA Results

This note records the audit findings for the targeted dynamic no-mitigation
results. It is intentionally conservative.

## Clean/Usable Outputs

The following files are internally consistent for the targeted topology/status
FDIA experiment:

- `targeted_attack_search_34bus.csv`
- `targeted_selected_cases_34bus.csv`
- `targeted_method_comparison_34bus.csv`
- `table_targeted_method_summary_34bus.csv`
- `table_targeted_detection_summary_34bus.csv`
- `targeted_dynamic_no_mitigation_manifest.json`

Audit checks:

- Selected-case mean/max impacts match the replayed comparison rows.
- `targeted_method_comparison_34bus.csv` has no non-finite, negative-energy,
  out-of-bound energy-ratio, excessive-impact, or convergence-violating rows.
- The selected cases are paper-valid according to the script filters.

## Major Methodology Condition

These results are not the same as the earlier measurement-only FDIA experiment.
They are a targeted topology/status FDIA experiment.

The selected cases use:

- base `topology_drop` observation corruption, plus
- `false_topology_status_to_action_mask`, where false topology/status data marks
  selected actions as unavailable.

This is recorded in the CSV metadata as:

- `attack_surface = observation_plus_decision_channel`
- `decision_channel_projection = false_topology_status_to_action_mask`

Therefore the paper must describe this as topology/status FDIA against outage
management decision inputs. It should not claim that voltage masking or
branch-flow hiding alone caused MLP/BPSO impact.

## MLP Condition

The saved 34-bus MLP policy was observed to be effectively constant under
feature-only FDIA probes. In the targeted results:

- MLP raw policy action changed rate is `0`.
- MLP final dispatched action changed rate is `1`.
- MLP impact is caused by corrupted DMS feasibility/status filtering, not raw
  MLP feature sensitivity.

This can be defensible only if the methodology explicitly models a DMS
feasibility/availability layer after MLP.

## BPSO Condition

BPSO impact is caused by corrupted perceived status/objective inputs during
optimization. This is different from the earlier strict observation-only FDIA
run, where BPSO had zero impact.

The paper should state that BPSO is attacked through the cyber data used by the
optimizer/feasibility model.

## Older Strict FDIA Results

The earlier strict common FDIA experiments showed:

- GRL/GCAPS: nonzero impact under topology/voltage attacks.
- MLP: zero impact.
- BPSO: zero impact.

Those strict results must not be merged with the targeted topology/status
results without clearly saying that the threat model changed.

## Profile Export Warning

The energy-served profile files were corrected to use the accepted
`targeted_method_comparison_34bus.csv` values.

However, the per-bus voltage profile files were generated by replaying selected
actions because the original targeted run did not save full bus/phase voltage
matrices. Audit comparison found that replayed voltage min/max values can differ
from the accepted comparison metrics for at least one selected BPSO case.

Therefore:

- `profile_energy_served_34bus.csv` is usable for energy-served plots.
- `table_energy_served_by_method_34bus.csv` is usable for GCAPS/MLP/BPSO
  energy-served plots.
- `profile_voltage_bus_phase_34bus.csv` and
  `table_voltage_profile_summary_34bus.csv` should not be used as final paper
  voltage-profile evidence until the main targeted experiment is rerun with
  voltage logging integrated into the same simulation pass.

## Required Next Step For Fig. 6-Style Voltage Plots

Rerun the targeted experiment with full bus/phase voltage logging inside the
same clean/attacked dynamic trajectory generation that writes the impact rows.
That will make voltage profiles, energy served, impact metrics, and actions all
come from the exact same simulation pass.
